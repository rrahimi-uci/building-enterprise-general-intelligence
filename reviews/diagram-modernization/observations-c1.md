# Technical observations, group c1 (raised, not changed)

Figures: `developer-platform`, `gateway-roles`, `knowledge-fabric`, `portability`, `runtime-boundary`, `runtime-offline`, `security-boundaries`. None of these was acted on; every figure keeps the original semantics.

1. **`developer-platform` (Figure 7-1): the stacking has no drawn relationship.** The source's edges between the four tiers are all `style=invis`, so the figure only implies order (team-owned, SDK, platform, control). The restyle draws no connector. If the message is "each tier depends on the one below", a visible arrow would say it; the "Control" tier's name ("never re-implemented by a team") also reads like a cross-cutting layer rather than the bottom of a stack.
2. **`gateway-roles` (Figure 1-4): "Systems of record" has two inbound edges with different gating.** `tool -> sys` ("read or pre-approved") and `approval -> sys` ("approved once") both land on the same store, but the first is drawn solid and the second leaves a diamond; the text does not say whether a "pre-approved" effect still passes the human-approval check earlier. Kept as in the source.
3. **`gateway-roles`: the "Agent runtime" to "A2A Gateway" edge is double-headed (`dir=both`) and dashed,** the only bidirectional edge in the figure, while the other external gateways (LLM, MCP) are one-way and the replies (model response, MCP result) are not drawn. A reader may infer that only A2A has a return path. Kept as in the source.
4. **`knowledge-fabric` (Figure 5-1): the "governs" edge stops at the representations row.** The Governance bar lists "release", "permissions" and "pinned release", but the only governs edge goes to the four representations; the Knowledge resolution API also says "permissions enforced here". As drawn, governance does not visibly govern the API surface. Kept as in the source.
5. **`knowledge-fabric`: row colours.** The four representation cells are blue, cyan, red and plum in the source (red is the book's failure colour elsewhere); here "Rules" is red only because the source made it so. Kept; the red role means "failure/refusal" in the style guide, so this is the one place it marks a content type.
6. **`portability` (Figure 7-2): "swap" edges land on the groups, not on a member,** deliberately (the source comment explains it), but the dotted "or" edges join only the two members of each group; "or" between Agents SDK / Graph runner and between Model A / Model B is the only statement that the adapters are alternatives. Fine as drawn; noted because the two-member count may read as "exactly two".
7. **`runtime-boundary` (Figure 3-1): "AgentStepResult" is linked to the receipt by a dotted "linked evidence" edge, but nothing links "Refuse" to any evidence record.** A refusal has no receipt in the drawing. Kept as in the source.
8. **`runtime-boundary`: the cluster is called "no enterprise authority" but also contains the "Model provider" node,** a platform-contracted external. The cluster edge to "AgentStepResult" ("structured outcome") leaves the cluster, not the agent loop. Kept.
9. **`runtime-offline` (Figure 25-2): the bridge starts at "Stop, ask, or escalate" only.** Runtime outcomes cross as evidence "not a change", but the figure draws the crossing from the last runtime step alone, although the retry/fall-back and context decisions also produce trace evidence. Kept as in the source.
10. **`security-boundaries` (Figure 20-2): the "Model provider" is outside the boundary but the only edge is a one-way "prompt".** The model's response (untrusted output) is not drawn; "Agent runtime" carries the label "untrusted output" instead. Kept.
