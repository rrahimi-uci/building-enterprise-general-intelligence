### 2.2 What is missing (expand) — in chapter order

1. **A layer model.** "Each representation… is derived from—and traceable back to—the source above it" asserts a derivation chain that is never drawn. The chapter uses *artifact*, *representation*, *view*, *model*, *rule*, *constraint*, *snapshot*, and *version* without saying which are things, which are encodings, which are services, and which are decisions. § 3 supplies the model.
2. **Ontology and knowledge graph as representation.** § Ontology and knowledge graph says what traversal buys and warns that ontologies kill programs; it never says what an ontology *is* here (the schema the graph must conform to), how statements are encoded (RDF triples with OWL/SKOS vocabularies, or property-graph records), that conformance is checked (SHACL-style shapes), or that the graph is a versioned instance with a digest. "Reasoning" is left open to an OWL-entailment reading the book does not intend.
3. **Who may change knowledge, and how a change becomes a version.** "Version and supersedes", "Lifecycle: review cadence and expiry", "has an eligible owner approve", "the rule version used for each case", and the PRODUCTION CONSIDERATION box all presume a lifecycle that no section defines: no change unit, no gates, no definition of "eligible", no publication step, no rollback, no deprecation. The ingestion plan explicitly deferred the lifecycle state model, stewardship eligibility, and quality-and-freshness measurement to this plan (its § 3 table).
4. **Control plane vs runtime plane.** The chapter has a Hub (runtime) and an extraction pipeline (control plane) but never separates them or names the interface. Chapter 4 § Global control and regional cells already places "signed, immutable definitions" in the global tier and runs in cells; knowledge should follow that split explicitly.
5. **What "approved knowledge" means at each control point.** The chapter enforces one rule at the effect boundary (`rule-as-guardrail`). It does not say how the Context Service, plan compiler, policy decision point, Tool Gateway preconditions, or acceptance engine consult the pinned release, nor what each does when knowledge is missing, ambiguous, stale, or contradicted. Chapter 12's compile-time checks and Chapter 13's "deterministic domain rules" both silently depend on it.
6. **Monitoring and feedback.** No metric or feedback path exists for knowledge (AP-09's "evidence age… citations pointing at superseded revisions" is the nearest). Chapter 25's improvement table has no Knowledge row.

## 4. Control plane vs runtime plane

Detail: `knowledge-cicd-model.md` § 1.

- **Control plane** (global control tier): creation, extraction, modelling, validation, versioning, testing, approval, publication, promotion, rollback, deprecation, retirement. Writers: knowledge owners and SMEs; the extraction/curation assistant proposes staged edits and holds no write credential; the **publishing controller** is the single service identity that merges, releases, and activates. Holds no run state.
- **Runtime plane** (regional cell): resolve once at admission, then retrieve, traverse, query, evaluate, enforce — over approved knowledge only, read-only. Consumers are the book's control points (§ 6). The runtime never writes knowledge; memory (Chapter 6) is a different store with a different gate, and a promoted memory can only become a *proposed* knowledge change.
- **Interface.** Down: the KnowledgeRelease manifest and content-addressed bundle; the live pointer (an EnvironmentBinding scoped to a knowledge stream, per tenant · environment · region); the run's resolution recorded in `knowledge_snapshots`; the Hub's read-only operations `:resolve` (admission only), `:search` (Chapter 6), `:query` (bounded traversal), `:evaluate` (three-valued), `GET releases/{digest}` — every one takes a release digest, none accepts "current". Up: decision records (release digest, rule ids, verdict), refusals, runtime contradictions, superseded-release citations, acceptance defects, evaluation results, SME feedback, and the ChangeBundle drafts the learning loop produces (Chapter 25). Evidence crosses up; writes never do.
- **Ties to existing records.** The ReleaseManifest (Chapter 27) declares which knowledge *streams* an agent release accepts and the ontology major versions it is compatible with; the RunManifest (Chapter 4) records the release *digests* resolved at admission; every ContextManifest segment of kind `enterprise_data` (Chapter 6) carries the release digest alongside its source revision; every decision span (Chapter 24) cites the digest and the rule ids. Chapter 27's "current under freshness policy" reproducibility level is restricted to the Semantic view's retrieval index (inventory row 27.2); normative and structural knowledge are always a recorded release.

## 5. Knowledge CI/CD lifecycle

Detail: `knowledge-cicd-model.md` §§ 2–6 (vocabulary mapping, the stage table, change unit, branching, the nine gates with limits, states, publication semantics, deprecation, monitoring, the breaks in the analogy, the Harborlight thread). Summary of the decisions the chapter will state:

- **Stage mapping.** Source → knowledge objects; lockfile → pinned upstream base release; feature branch → knowledge change with a frozen candidate identity; build → deterministic resolution of base + overlay + ontology into a content-addressed effective release; lint → named gates; tests → knowledge test suite and impact diff; code review → independent SME approval; registry → knowledge registry; tag → stream version + digest; deploy → pointer activation by the controller; promotion → identical digest; rollback → prior Active release by pointer; monitoring → decision records and refusals; feedback → ChangeBundle draft. Full table with book components in the model file § 3.
- **Change unit.** One change names its objects by stable id, its rationale and source digests, and its version bump; it resolves to one candidate; it never deletes a released object (it deprecates). Ontology changes are schema migrations with a coexistence window.
- **Branching.** One change, one branch; no long-lived knowledge branches (staleness); tenant deviations are overlays over a pinned shared base, never forks of the ontology; a redesign is a new major stream; hotfixes use the same path with priority review and documented break-glass.
- **Gates (named checks), all on the effective release:** `knowledge-schema` (SHACL-style shapes / graph schema / rule contract), `grounding` (independent re-verification against pinned source digests), `change-contract`, `consistency` (deterministic contradictions over typed rules on one subject across base + overlay; undefined terms and unplaceable concepts held for review), `duplicate-overlap` (digest-exact deterministic; semantic advisory only), `staleness` (touched revisions, base pin, candidate identity, approval identity), `regression` (golden decision and refusal cases, traversal and shape fixtures, four-way impact diff with nothing dropped and `review-held` never auto-resolved), `independent-approval` (a different eligible human on the exact identity), `publication-readiness` (bundle stored and verified before the pointer moves; version allocated once; compare-and-swap on the pointer).
- **States.** Draft → Certified → Approved → Active → Deprecated → Revoked, reusing Chapter 8's names plus a mandatory Approved state, because knowledge has no automated oracle for meaning. Retired releases are retained while any RunManifest in retention references them.
- **Environments and promotion.** Staging → UAT → production per tenant, identical digest; a diverged target blocks. **Activation is the publication boundary.** Publish failed leaves the old release live; retry is idempotent.
- **Rollback, deprecation, retirement.** Pointer moves back; history is never rewritten; in-flight runs keep their pin unless the release is revoked; open changes become Stale. Deprecation is a release decision with a compatibility window equal to the longest admitted run plus the replay horizon.
- **Monitoring and feedback.** `unknown` verdicts per rule, refusals per rule, runtime contradictions, superseded-release citations (AP-09), SME corrections, slice regressions after a knowledge release — each with a fixed denominator, each evidence into the control plane, none a write.
- **Where the analogy breaks** (the chapter states these as a short list): correctness is semantic; authors are not engineers; a clean merge is not valid knowledge; audit carries compliance weight and repository history is not the archive; knowledge has an upstream supply chain; pinning is per run; ontology changes are migrations; a graph diff is not a meaning diff; contradiction can be legitimate (scope); the test suite is thin by default and must report its own size.

## 12. Self-critique

**Established vs proposed.** Established and cited: RDF triples/graphs/datasets [R55], OWL 2 ontologies [R56], SHACL shape validation [R57], SKOS vocabularies [R58], PROV-O lineage relations [R59], DMN/SBVR/BPMN/CMMN [R44]–[R47], the single measured figure [R48]. Established practice but uncited in the book and left uncited here, consistent with Chapter 27's existing "GitOps-style promotion": trunk-based change, immutable content-addressed artifacts, environment promotion of identical bytes, pointer-based rollback. Proposed (book-authored): everything else in §§ 3–6, including the layer model, the nine gates, the Approved state, the publishing controller, and the control-point table. The chapter must not let the W3C citations lend authority to the lifecycle.

**Claims removed or softened while writing this plan.** (1) "Knowledge graphs enable reasoning" — softened to bounded traversal and deterministic decision evaluation; OWL entailment at runtime is not proposed because its results depend on reasoner, profile, and completeness, which would make a control point's decision non-reproducible across releases. (2) "SHACL validates the knowledge graph" — only for RDF; for property graphs the chapter says "schema constraints" and the example is a toy. (3) "GQL is the ISO property-graph standard" — conditional on verifying the ISO page; not asserted otherwise. (4) "Automated contradiction detection" — restricted to typed rules on one subject; no rate claimed. (5) "Clean merge is not valid knowledge" is kept, but as design rationale, not as a measured finding. (6) Nothing from mental model B is presented as implemented or as evidence; its phrases that remain ("activation is the publication boundary") are adopted as book-authored rules.

**Known limits of automated contradiction and duplicate detection.** Deterministic contradiction detection sees only rules whose subject, scope, and predicates align in the typed contract; prose rules, rules using synonyms the vocabulary has not reconciled, scope-conditional conflicts, and numeric ranges that overlap partially are not detected, and a conflict between two jurisdictions is scope rather than contradiction. General consistency of a constraint set is undecidable in the general case and expensive in the bounded cases; the chapter therefore presents the gate as a filter that reduces what the SME must read, never as proof of consistency. Duplicate detection by content digest misses paraphrase; embedding similarity finds paraphrase and false friends alike and is advisory only (the chapter's existing rule). Policy Logic Forge's own experience — relationship claims rejected at 44% by an independent pass, dangling references that nothing validated, over-reported type conflicts — is the evidence that these checks need an independent verifier and a human, not that they are solved.

**Where realistic enterprise practice differs from the pipeline.** Most knowledge lives in document stores and wikis with no stable ids; the first "release" is a digest of a folder.
