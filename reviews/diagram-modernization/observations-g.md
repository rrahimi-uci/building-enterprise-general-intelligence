# Observations, group g (sequence diagrams): raised, not changed

Both figures keep every participant, message, frame and note of the original. These are technical doubts about the originals, left as drawn.

1. **`request-sequence` (Figure 4-2): no refusal or denial branch.** "grant, or refusal" (Policy to Run) and "approval decision" (Approval to Run) can both be negative, but the sequence continues unconditionally to "invoke with logical effect key". Only the approval step is wrapped (opt [protected change]). A reader may conclude the run always reaches the Tool Gateway. Guardrail-sequence (Figure 20-3) does show the refusal branch; the two figures disagree on how much of the denial path to draw.
2. **Who calls the Tool Gateway differs between the two figures.** In `guardrail-sequence` the Policy Engine sends the "authorized invocation" to the Tool Gateway; in `request-sequence` the Run Service invokes the Tool Gateway after receiving the grant. Plausibly different levels of abstraction (the platform is drawn as one Run Service in 4-2), but the chapters should confirm that the second is not a different control flow.
3. **`request-sequence`: the opt frame spans Run Service to Approval Service only.** The note "the model proposes, the platform decides" spans Run Service to Policy & Identity. Both are as in the source; no doubt about correctness, noted because the frame and the note have different extents.
4. **`guardrail-sequence`: the Content detector is not a lifeline for any message after its finding.** As drawn, the detector never learns the outcome and the refusal goes to the Agent Runtime, consistent with the stated message ("the detector only raises a finding"). Noted only as it makes the detector a leaf.
5. **Visual encoding, not content.** The original rendered dotted `-->>` returns as dashed lines; the restyled figures draw them dotted (the style guide's dotted flow) and draw lifelines dashed, so the two kinds stay distinguishable. The source's actor stick figure is a capsule header with a person icon.
